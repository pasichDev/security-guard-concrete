# Security Guard for Concrete CMS — специфікація v1.0

Copyright (c) 2026 Andrii Pasichnyk. All rights reserved. See LICENSE.

Пакет Concrete CMS 9.x (перевірено на 9.5.2, PHP 8.2) — веб-фаєрвол і панель
безпеки в адмінці. Порт і переосмислення `pasichDev/security-guard-joomla`
(Joomla 3.10) під Concrete: та сама функціональність, але з урахуванням
уроків реального shared-хостингу (CloudLinux, ліміти ресурсів, `exec` вимкнено).

## Цільове середовище й жорсткі обмеження

- Shared cPanel, CloudLinux LVE. Хостинг уже віддавав 508 (ліміт ресурсів).
- `exec`, `shell_exec`, `system`, `popen`, `escapeshellarg`, `posix_*` вимкнені.
  Не використовувати. `gethostbyaddr`/`gethostbynamel` дозволені.
- Перед Apache стоїть nginx; статику nginx віддає сам, PHP її не бачить.
- Ядро Concrete (`concrete/`) не чіпати. Усе — у пакеті.
- Код без зовнішніх залежностей Composer (лише ядро Concrete). Без зовнішніх
  мережевих API (геолокація — офлайн).

## Принципи (обов'язкові)

1. **Fail-open.** Будь-який виняток у гарячому шляху (обробка запиту) ловиться,
   пишеться в лог Concrete, і запит пропускається. Пакет ніколи не кладе сайт.
2. **Дешевий гарячий шлях.** На звичайному запиті — жодного запиту до бази.
   Стан, потрібний на кожному запиті (активні бани, білий список, конфіг),
   читається з одного PHP-файлу-кешу (`opcache`-дружній `return [...]`),
   який перебудовується при зміні (бан/розбан/зміна налаштувань) атомарно
   (запис у тимчасовий файл + `rename`). Лічильники частоти — APCu, якщо
   доступний, інакше файлові лічильники в `application/files/security_guard/`
   з `flock`, з очищенням. Запис у базу — лише при подіях (атака, бан,
   honeypot, невдалий вхід), і з тротлінгом.
3. **Режими:** `monitor` (за замовчуванням після встановлення — тільки
   журналювати, нічого не блокувати), `enforce` (блокувати). Перемикач у
   налаштуваннях і помітний банер на панелі, поки режим `monitor`.
4. **Ніколи не заблокувати адміна чи редактора.**
   - Користувач, що увійшов і має доступ до дашборду, обходить усі евристики.
   - Запити до `/dashboard`, `/ccm/`, `/index.php/ccm/`, `/login` (крім
     захисту від підбору пароля) не проходять через евристики вмісту
     (редактори постять HTML з `<script>`, `../`, `union` тощо).
   - Автодовіра IP після успішного входу адміністратора на N днів.
   - Аварійний обхід: `?sg_pass=<секрет>` знімає бан з поточної IP (секрет
     порівнюється `hash_equals`, порожній = вимкнено).
   - Кнопка «Розблокувати мою IP» на панелі, з показом поточної IP.
5. **Справжня IP клієнта.** `REMOTE_ADDR`, якщо він не з довірених проксі.
   Довірені проксі — налаштування (CIDR). Cloudflare-діапазони — опція.
   `X-Forwarded-For` читати з кінця, пропускаючи довірені. Ніколи не довіряти
   заголовкам від недовіреного джерела.
6. **Не ламати легасі-редиректи.** Сайт мігрований з Joomla; старі адреси
   типу `/index.php?option=com_content&view=article&id=…` мають редиректи.
   Правила проти Joomla-експлойтів — лише точкові (конкретні `option`+`task`),
   не блокувати `option=com_content` / `com_contact` / звичайні перегляди.
7. **Безпека самої панелі.** Усі дії — POST з токеном `ccm_token`
   (`$this->token->validate()`), перевірка прав (`canAccessSecurityGuard`),
   екранування виводу (`h()`), жодного виводу сирих URL/UA без екранування.
8. **i18n.** Усі рядки інтерфейсу через `t()`. Українська — основна мова
   інтерфейсу; англійська — вихідні рядки в `t()`. Переклад uk_UA у
   `languages/uk_UA/LC_MESSAGES/messages.po` (+ `.mo`).
9. Кожен файл — заголовок
   `Copyright (c) 2026 Andrii Pasichnyk. All rights reserved. See LICENSE.`

## Функціональність

### A. WAF (гарячий шлях)
Порядок перевірок на кожному фронтенд-запиті (раннє подія пакета):
1. Аварійний обхід `sg_pass`.
2. Білий список (loopback, префікси/CIDR з налаштувань, автодовіра адмінів),
   залогінений користувач з доступом до дашборду → пропуск.
3. Активний бан → відмова (403 або 429 для бану за підбір пароля), лічильник
   спроб забаненої IP (тротлінг запису).
4. Верифіковані пошукові боти (Googlebot, Bingbot, YandexBot, DuckDuckBot,
   Applebot, Baiduspider…): rDNS + прямий DNS підтвердження, кеш результату.
   Фейковий бот (UA пошукача, rDNS не збігся) → бал/бан.
5. Honeypot-URL (список + власні) → бан одразу + запис.
6. Погані User-Agent (сканери, HTTP-бібліотеки, AI-краулери — окрема група,
   вмикається окремо).
7. Сигнатури атак (URI + query + тіло POST для фронтенду): SQLi, XSS у
   параметрах, обхід каталогів, `/etc/passwd`, виклики коду, Joomla-експлойти
   (JCE, com_ajax upload, SP Page Builder uploadCustomIcon, RSFiles, Gridbox,
   helix3), WordPress-пробінг, веб-шелли (відомі імена, hex-імена,
   PHP у теках завантажень, подвійні розширення), чутливі файли
   (`.env`, `.git`, бекапи конфігів, `composer.*`). Кожне правило має код
   (напр. `SQL_UNION`) і категорію (wordpress / joomla / secrets / shells /
   injection / scanner / honeypot / bruteforce / ratelimit / behavior / ddos / geo / bot).
8. Сплеск PHP-проб (N запитів до `.php` за T секунд з однієї IP) → бан.
9. Ліміт частоти (N запитів за T секунд на IP; статика виключена).
10. Поведінковий скоринг (порожній/короткий UA, нема Accept/Accept-Language,
    POST без Referer, довгий query, пробні шляхи) з TTL; поріг → бан.
11. Гео-блок (опційно, за кодом країни, офлайн-визначення за префіксами;
    можна вимкнути).

Ескалація банів: 1 год → 24 год → 7 днів → 30 днів для повторних порушень.
Відповідь: налаштовуваний код (403 за замовчуванням, 404 як «тиха» опція),
коротка сторінка без деталей. У режимі `monitor` — тільки журнал.

### B. Захист входу
- Невдалі входи (подія Concrete на невдалу автентифікацію) рахуються на IP у
  вікні; поріг → бан з причиною `BRUTEFORCE`, відповідь 429 на сторінці входу.
- Узгодити з вбудованим механізмом Concrete (IP access control / failed login
  ban у Dashboard → System → Permissions): не дублювати конфліктно. Якщо ядро
  має сервіс бану за невдалі входи — використовувати/показувати його стан, а
  наш лічильник — як доповнення з ескалацією та сповіщенням.
- Сповіщення на e-mail адміна (налаштовуваний список) про: бан за підбір
  пароля, виявлений DDoS-сплеск, вхід адміністратора з нової IP. З тротлінгом
  (не більше одного листа одного типу на 15 хв).

### C. Журнали й дані (база, Doctrine-сутності пакета)
- `SecurityGuardBlock` — ip, reason, category, blocked_until, attempts,
  escalation_level, first_seen, last_url, last_user_agent, created/updated.
- `SecurityGuardEvent` — журнал атак: ip, rule, category, action
  (logged/blocked), method, url, user_agent, referrer, country, created_at.
  Тротлінг однакових записів; автоочищення старших за N днів.
- `SecurityGuardWhitelist` — prefix/CIDR, description, expires_at (для автодовіри).
- `SecurityGuardScore` — ip, score, events(json), updated_at (TTL).
- `SecurityGuardBotCache` — ip, hostname, is_bot, bot_name, verified_at.
- `SecurityGuardDailyStat` — агрегати з логів хостингу по днях:
  day, total_requests, attack_requests, attack_ips, blocked_403, login_fail,
  overload_508, errors_404, errors_5xx, bytes, unique_ips, + JSON розбивки
  (категорії атак, топ IP, топ URL, топ країн, по годинах). Ідемпотентно:
  перерахунок дня перезаписує рядок.
- `SecurityGuardLogCursor` — для кожного файла логу: шлях, inode/розмір,
  позиція, хеш першого рядка — щоб не рахувати двічі при ротації.
- `SecurityGuardAlert` — type, severity, message, value, baseline, ip, url, created_at.

### D. Аналітика логів хостингу
- Джерела налаштовуються: за замовчуванням `~/access-logs/<домен>-ssl_log`,
  `~/access-logs/<домен>`, архіви `~/logs/<домен>*.gz`. Читати через
  `gzopen`/`fopen` (без `exec`). Формат — Apache combined.
- Запуск: команда Concrete (CLI `c5:security-guard:ingest`) для cron +
  кнопка «Оновити зараз» на панелі (обмежена за часом виконання, дочитує
  з курсора). Ідемпотентність: агрегати дня перераховуються з сирих рядків
  цього дня; курсор не дає читати одне й те саме двічі; ротація архівів
  розпізнається.
- Класифікація атак у логах — тими ж правилами, що й у WAF (один спільний
  клас правил).
- Режим сумісності зі звітом (`security-guard:stats --report-compat`): атакою
  вважається запит, URL якого відповідає (без урахування регістру) регексу
  `wp-|xmlrpc|\.env|\.git|phpmyadmin|eval\(|shell|option=com_|/(zwso|xxx|alfa|wso|c99|r57|up|cmd|bypass|admin)\.php|\.\./|union.*select|/etc/passwd`.
  Основна класифікація (RuleSet) точніша; кожен день зберігає обидва набори цифр.

### E. Виявлення DDoS і сплесків
- По хвилинних кошиках (APCu/файл): поточна частота vs ковзна базова лінія;
  множник і мінімум запитів — налаштування. Сплеск → `SecurityGuardAlert`,
  опційно автобан топ-IP сплеску, лист.

### F. Адмінка (single pages пакета під `/dashboard/security_guard`)
- **Огляд** — стан захисту (режим, увімкнені модулі, бали за чеклистом),
  плитки (атаки сьогодні/7 днів/30 днів, активні бани, невдалі входи,
  перевантаження), графіки по днях (атаки, усі запити, 508), розподіл за
  категоріями, топ атакуючих IP і країн, останні події, сповіщення.
  Фільтр періоду (7/30/90 днів/довільний). Графіки — власний легкий SVG/JS
  без CDN (CSP-дружньо), з тултипами, у стилі адмінки Concrete (Bootstrap 5).
- **Журнал** — події з фільтрами (категорія, дія, IP, дата), пагінація,
  експорт CSV.
- **Бани** — активні/історія, розбан, бан вручну, «бан назавжди», моя IP,
  «розблокувати мою IP».
- **Білий список** — CRUD, автодовірені з терміном.
- **Honeypot** — влучання, список пасток.
- **Скоринг** — IP з балами.
- **Трафік** — дані з логів хостингу: по днях/годинах, топ URL, 404, 5xx,
  статуси, боти, кнопка «Оновити з логів».
- **Перевірка безпеки** — чеклист середовища: права `application/config`
  (має бути не ширше 0750/0640), PHP-файли у `application/files`, файли з
  правом запису для всіх, доступність `.env`/`.git`/`config` ззовні (через
  self-HTTP-запит до власного домену), заголовки безпеки, версія Concrete/PHP,
  режим налагодження вимкнено, ввімкнений кеш. Кожен пункт: стан + що робити.
- **Налаштування** — усі параметри модулів з поясненнями.
- Картка на стартовій сторінці дашборду (елемент пакета, який сайт може
  вставити у свій `welcome.php`): режим, атаки сьогодні, активні бани,
  посилання на панель.

### G. Обслуговування
- Автоочищення старих записів (подія/команда, тротлінг).
- `install()`/`upgrade()` ідемпотентні; `uninstall()` прибирає таблиці,
  конфіг, файли кешу.
- Версія пакета — `$pkgVersion` у контролері; зміни схеми — через сутності +
  `upgrade()`.

## Що НЕ робимо
- Не пишемо кожен запит у базу (так робила Joomla-версія; на цьому хостингу це
  дає 508).
- Не викликаємо зовнішні API (геолокація, репутація IP).
- Не змінюємо `.htaccess` сайту автоматично.
